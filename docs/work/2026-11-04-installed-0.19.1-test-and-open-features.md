## Smoke test of the installed tool

The test used the global tool `ai-proxy` 0.19.1, with a live instance started by `ai-proxy --restart` and listening on 8080, API on 17432.

| Check | Result | How |
|---|---|---|
| `--version` | `0.19.1` | CLI |
| Pass-through of a non-provider host | 200, TLS tunnelled | `curl -x 127.0.0.1:8080 https://example.com` |
| Provider inspection | Leaf `CN=api.anthropic.com` issued by `CN=ai-proxy local inspection CA`; upstream 401 relayed unchanged | `curl -v -x ... https://api.anthropic.com/v1/messages` without a key |
| Name-constrained root (ADR 0009) | `X509v3 Name Constraints: critical`, permitted `openai.com`, `anthropic.com`, ...; valid to 2036 | `security find-certificate` piped to `openssl x509 -text` |
| `gain` text and `--format json` | Both render live store totals (4,8xx requests) | CLI |
| `mcp` `initialize` and `tools/list` | `retrieve_original` advertised, logs on stderr only | JSON-RPC over stdio |
| `mcp` `tools/call retrieve_original` | Returned lines 1 to 3 of a preview this session had just received | JSON-RPC over stdio |

Two defects showed up:

1. **The gain table splits numbers mid-digit at 80 columns** (`271,78` over `0,847`). This is F1 of the 2026-10-31 record. It is fixed on main in 0.19.2 but isn't published, so installed users still see it.
2. **`ai-proxy mcp` drops replies still in flight when stdin closes.** If you pipe three requests and close stdin, the handlers run (the log says they completed) but nothing reaches stdout. If you keep stdin open for three seconds, every reply arrives. Real MCP clients keep stdin open, so this is low impact. A script, or a CI smoke test, will see empty output, though. Not yet filed.

## musl code views (checked 2026-11-05)

TreeSitter.DotNet 1.3.0, the newest release, ships natives for linux-x64, arm, arm64 and x86, osx and win, but none for linux-musl. So the `ai-proxy.linux-musl-x64` payload carries the glibc `libtree-sitter.so`, byte-identical to the linux-x64 one. Its SQLite native, by contrast, is a real musl build.

The `musl-code-view` CI job runs the 170 code-view tests in the .NET SDK Alpine image (`10.0.403-alpine3.24`, pinned by digest). They pass, and `gcompat` is not installed. The job can fail: with `libtree-sitter.so` deleted, the run failed with `DllNotFoundException` ([PR #109](https://github.com/Arasz/ai-proxy/pull/109), red-proof commit `38b48b5`).

The pass is fragile. `ldd` on the same file in the same container reports `__snprintf_chk`, `__vsnprintf_chk` and `__fprintf_chk: symbol not found`. In the test process some other loaded library must provide them. That is an inference: I didn't find which library it is. The installed tool runs on the smaller runtime-deps image, where the set of loaded libraries can differ, and nothing has tested that yet. When a grammar fails to load, the proxy logs one warning per grammar and sends the original text, so the failure costs compression, not correctness.

Owner decision still open: build a musl `libtree-sitter` and ship it in the musl payload (about a day, and a second native supply chain), or document that code views on Alpine are best effort. The canary job stays either way, so it flags the day the behaviour changes.
