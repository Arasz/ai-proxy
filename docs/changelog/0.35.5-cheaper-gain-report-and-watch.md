# 0.35.5: cheaper gain report and watch

`ai-proxy gain --watch` asks the proxy for the whole gain report every 2 seconds. A live trace of
0.35.4 showed that this report used about 99% of the proxy's CPU (24% of one core) and made about
78% of its allocations. The proxy traffic itself was under 1%. The report now reads each ledger
value once, the proxy keeps the last report until the ledger changes, and the watch view redraws
only when the report changes. The decision is
[ADR 0024](../adr/0024-gain-report-reads-each-value-once-and-is-cached.md).

## Changes

- **Each ledger value is read once.** The report statement reads the sixteen totals of a row into
  columns one time, and every view sums those columns. The totals come back as columns, not JSON
  text, so the store does not parse them again.
- **The last report is cached.** The store keeps the last report with its filters and the ledger
  version (`MAX(sequence)` and `COUNT(*)`). The same filters on the same version get that report
  with a new `GeneratedAt`. A recorded event or a reset makes the next query run again, also when
  another process wrote it.
- **Attribution sums in place.** `GainReportBuilder.Sum` and `Attribute` add into one accumulator
  for each name and split rule paths without substrings.
- **The watch view redraws only on change.** `gain --watch` gives the live display a new target
  only when the report, except its generated time, changed.

## Measured

On a copy of a live ledger (65,000 rows, 12,283 requests):

| Report | Before | After |
|---|---|---|
| Not cached | 0.52–0.94 s, about 1 MB allocated | about 0.21 s, about 450 KB |
| Cached | not cached | 2 ms, 7 KB |
| One rule attribution pass (260 rows) | 377 KB | under 16 KB |

## Upgrade

No action. The ledger schema does not change.
