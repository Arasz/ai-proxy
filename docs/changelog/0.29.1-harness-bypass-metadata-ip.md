# 0.29.1: harness sessions skip the proxy for the cloud metadata address

`ai-proxy harness` now adds `169.254.169.254` and `169.254.0.0/16` to the child's `NO_PROXY` and `no_proxy`, after any bypass entries you already had and after `localhost,127.0.0.1,::1`.

Before this release, an SDK in a harness session that probed the cloud metadata address (AWS, GCP and Azure credential chains, OpenTelemetry resource detectors) sent the probe through ai-proxy. Off a cloud VM nothing answers, so the proxy tried to connect for its full 20 s connect timeout, logged `timeouts (Enforce): connect timeout exceeded ... host 169.254.169.254` at `fail` level and returned 504. The client saw no change in speed, because its own short timeout fires first and a direct probe also hangs; the cost was a held proxy connection and a false failure in the log. The macOS system proxy already skips `169.254/16`, so only the harness environment was affected.

The literal address covers HTTP stacks that match `NO_PROXY` by host only, such as Node's `proxy-from-env`; the CIDR form covers the rest of the link-local range for stacks that read CIDR, such as curl, Go and Python `requests`. Sessions started before the upgrade keep their old `NO_PROXY` until they are restarted.
