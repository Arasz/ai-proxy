# 0.28.6: never save a dead ai-proxy endpoint as the proxy to restore

Before this release, a start that skipped crash recovery saved whatever system proxy it found as the settings to put back at shutdown. If a crashed run had left HTTPS pointing at its own endpoint while you changed HTTP, that dead endpoint became the "original" proxy, and every clean shutdown after it restored HTTPS to a port nothing listens on.

Every start now cleans the settings before it saves them. Each HTTP or HTTPS value that is in effect and points at the previous run's endpoint, or at this run's own, takes the value the previous run saved before it changed anything. When there is no such value, or it points at ai-proxy as well, that protocol is turned off. Values another app set are kept, and so are proxies on another machine that use the same port. A value that is not in effect (switched off on macOS, outside manual mode on GNOME or KDE, off or overridden by a PAC URL on Windows) is left alone. Warning 1317 names the endpoints that matched. Titanium is given the cleaned settings too, so a failed set and its own exit restore put back the same thing.

On macOS, the check after a restore no longer compares the host and port of a proxy that is switched off, because macOS only flips the switch and leaves them as they were. Without this, restoring a cleaned value would have failed the check at every shutdown.

Two side effects: a proxy you set by hand to ai-proxy's own port is now turned off at shutdown, and after a shutdown that logged 1315 the next start turns a leftover HTTPS value off rather than restoring the proxy you had before ai-proxy, since that run's saved settings were deleted. [lifecycle](../reference/lifecycle.md#crash-recovery) describes both.

The system proxy platform's set step (`TitaniumSystemProxyPlatform`) now has unit tests that never touch real settings.
