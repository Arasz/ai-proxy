# 0.21.0: build output gets its own reducer

A `dotnet build` or `msbuild` log used to be read as plain prose. Prose reduction only drops
repeated lines, and build logs rarely repeat a line back to back, so a failed build went upstream
untouched. In a verbose log, two lines (the compiler command line and its response file) made up
most of the text.

Build output is now its own content kind. The proxy spots it by its diagnostics
(`File.cs(33,16): error CS0029: ...`) and its summary lines (`Build FAILED.`, `2 Error(s)`,
`Time Elapsed ...`). The restore and progress lines around them count as part of the same build log.

The new reducer keeps every error and warning line exactly as MSBuild printed it. It drops exact
repeats, which matters because MSBuild prints each diagnostic again in its end summary. A tool
invocation over 500 characters, a line made mostly of paths and switches such as the compiler
command line, keeps its first 200 and ends with a marker such as `[27712 characters dropped]`.
A long line of ordinary text is kept whole. The full text stays retrievable through `proxy_retrieve`. Build
output that none of these rules can shorten goes through the log reducer instead.

Measured on the two build logs in the scoring set:

| payload | before | after |
|---|---|---|
| `dotnet_build_failure.txt` | 902 characters, unchanged | 666 characters |
| `dotnet_build_failure_verbose.txt` | 60,672 characters, unchanged | 5,367 characters |

Test runner output (`dotnet test`) is not build output and keeps the kind it had.
