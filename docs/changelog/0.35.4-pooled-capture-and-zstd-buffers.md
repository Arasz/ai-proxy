# 0.35.4: pooled capture and zstd buffers

The response capture and the zstd decoder now take their buffers from a pool. A captured
response no longer allocates its payload buffers when the pool can lend them, and in the
benchmark it caused no gen2 collections. A zstd request body costs its decoded size once. The decision is
[ADR 0023](../adr/0023-pooled-buffers-for-zstd-decode-and-stream-capture.md). Shipped in
[#174](https://github.com/Arasz/ai-proxy/pull/174).

## Changes

- **Captured responses use pooled arrays.** An event stream rents its 64 KB head and tail. A
  whole body (up to 4 MiB) grows through rented arrays instead of a `MemoryStream`.
- **`ResponseBuffer.Read` replaces `ResponseBuffer.Body`.** The reader gets the kept bytes for
  the length of the call. An event stream is stitched into one rented array, with no scratch
  tail. One lock per buffer guards `Append`, `Read` and `Release`, so no write reaches an array
  after it goes back to the pool.
- **zstd bodies decode with the .NET 11 decoder.** It decodes into one pooled buffer sized from
  the frame, then copies the exact result once. It resets between frames, so a body of more than
  one frame decodes in full. ZstdSharp is no longer a dependency.

## Measured

Per response, appended in 4 KB chunks, read and released (BenchmarkDotNet, in-process):

| Body | Before | After |
|---|---|---|
| whole JSON, 1 MB | 206.7 us, 4,191,931 B, 235 gen2 per 1,000 | 67.6 us, 128 B, 0 gen2 |
| event stream, 256 KB | 148.4 us, 524,824 B, 83 gen2 per 1,000 | 120.7 us, 280 B, 0 gen2 |

zstd decode of a 512 KB body: 2,446,584 B before, under 512 KB + 32 KB after, for frames with
and without a declared size.
