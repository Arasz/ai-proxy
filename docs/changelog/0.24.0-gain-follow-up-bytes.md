# 0.24.0: `gain` counts the follow-up requests of retrievals and shows a billed balance

When the model asks for a preview's original, the proxy answers inside your request by sending a follow-up upstream. Until now `gain` never saw those requests, so a stateless session that resent a large body on every round still looked like a pure saving.

- Each follow-up the proxy sends is now recorded with its exact body length and an estimated token count. It is written only after the provider accepts it, so a refused follow-up adds nothing, and it works with request capture off.
- The summary table has a new Follow-up column, and a line under it reads `Billed balance (all requests)`: original minus forwarded minus follow-up tokens, with how many requests were measured. Net is unchanged. The balance leaves Retrieved out on purpose, because the retrieved text is already inside the follow-up bodies.
- Stateless follow-ups resend the forwarded body, so they cost a lot. Thread follow-ups send only the results and stay small. Both now show up.
- Follow-ups count in the summary and in the by-method, by-rule, by-layer and by-pipeline views, stamped with the time their request started. Daily, weekly and monthly buckets still list requests only.
- JSON totals gain `followUps`, `followUpBytes`, `estimatedFollowUpTokens`, `followUpMeasuredRequests` and `estimatedBilledBalanceTokens`; the schema version stays 1. CSV appends `follow_ups`, `follow_up_bytes`, `estimated_follow_up_tokens` and `estimated_billed_balance_tokens` after `bytes`; earlier columns keep their place.
- The summary table is a little tighter (no right padding) so its ten columns still fit an 80-column terminal.

Requests recorded before this release have no follow-up figures. They count as requests but not as measured, and the balance line is hidden until a measured request exists. Nothing is backfilled and no migration runs.
