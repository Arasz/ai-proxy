# 0.7.0: response usage and stage timings

**Released:** 2026-10-24
**PRs:** #37

With `PROXY_CAPTURE=on`, every captured request now also gets a row in a new `capture_response`
table of `~/.ai-proxy/capture.db`, under the same request id. The row says how many tokens the
provider counted (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`,
`cache_read_input_tokens`), the status code, the request size as sent and as forwarded, the
response size, and how long each step took, in microseconds: the proxy's own steps (reading the
body, writing the capture, each compression step, setting the body) and Titanium's (time to first
byte, response delivery, total). Comparing the two shows how much latency ai-proxy adds.

The response is never held back for this. Its bytes are copied as they stream past to the client
(the first and last 64 KiB of a plain event stream, any other body whole up to 4 MiB) and the
usage is read once the response is complete, gzip, deflate or br decoded. Usage is read for
Anthropic only, from a JSON message or an event stream; OpenAI's counts are not mapped, because
its prompt count includes cached tokens and Anthropic's does not. When the counts cannot be read
they stay empty and `usage_error` says why (`over-cap`, `encoding:<name>`, `decode-failed`,
`malformed`, `no-usage`, or `truncated` for a stream cut inside an event, which keeps the counts
read before the cut). Error responses get a row too. A failed response write is logged as a
warning (event id 1404) and the response is relayed anyway.

No response body and no response header is stored: the table has columns for numbers and the
reason only. A `capture.db` from 0.6.0 keeps its rows and gains the new table. With capture off
nothing changes.
