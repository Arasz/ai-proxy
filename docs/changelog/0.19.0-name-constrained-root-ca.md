# 0.19.0

ai-proxy now makes its own inspection root instead of letting Titanium make one. The new root,
`ai-proxy local inspection CA`, carries a critical name constraint. It can only vouch for hosts
under the provider domains the proxy inspects (`anthropic.com`, `openai.com`, `googleapis.com`,
`openrouter.ai`) and for no IP address. The old root could sign a certificate for any site, so a
leaked key was a key to everything the machine trusts. Now it covers only those domains.

Other changes to the root:

- Leaf certificates are never wildcards.
- The pfx has a random password, kept in `root-ca.password` with mode 0600. A password set in
  `Proxy:RootCertificatePassword` still wins.
- A pfx that cannot be opened stops startup and stays on disk. Before, Titanium silently replaced
  it.
- The dead `ProviderHostCatalog.ShouldInspectHttps*` helpers are gone.

## Upgrading

On first start, ai-proxy replaces the old root, trusts the new one and untrusts only the old one,
by thumbprint. Expect one trust prompt. Then **restart every harness session** (Claude Code,
Codex and the rest). They read `root-ca.pem` once, at start, through `NODE_EXTRA_CA_CERTS`, and
keep the old root until restarted. The proxy logs this as event 1308.

## Known gaps

- On Linux, the old root is not removed from NSS databases (`certutil`), so NSS-based browsers
  keep trusting it until removed by hand.
- A root is kept while it is still constrained. If a later release inspects a new provider
  domain, the root must be rotated (delete `root-ca.pfx` and restart) before that domain works.
- The chain tests run on Linux in CI. The macOS behaviour (it reports `InvalidNameConstraints`
  rather than `HasNotPermittedNameConstraint`) was verified locally only.
