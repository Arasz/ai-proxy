# 0.35.1: fewer body copies on the request path

The proxy copied each inspected request body several times. Request bodies are often larger
than 85 KB, so each copy went to the large object heap. A live proxy showed 51 MB of its 64 MB
managed heap on the large object heap, with 12 MB of it fragmented. Shipped in
[#171](https://github.com/Arasz/ai-proxy/pull/171).

## Changes

- **The region finder parses the body in place.** It copied the whole body before it parsed it.
- **The compression pipeline copies only when it changes the body.** It decodes the original
  text only when it replaces a region, rebuilds the output into one array of the exact size
  (it used a growing `MemoryStream` and then copied it), and writes each replacement as UTF-8
  directly.
- **The inspector forwards the compressed body without a copy.** It copied it once to forward it
  and again to record the gain. Now it uses the array the pipeline built.
- **Capture stores the request body without a copy.** It copied every captured body before it
  wrote it to `capture.db`, also when the body was not changed.

## Measured

Allocations for one call on a 1 MB body, from the allocation tests in
`ToolOutputRegionFinderTests` and `ContentCompressionPipelineTests`:

| Call | 0.35.0 | 0.35.1 |
|---|---|---|
| Find the regions | 1,050,872 B | 2,176 B |
| Compress, body unchanged | 3,150,792 B | 4,736 B |
| Compress, body changed | 7,395,024 B | 5,296,376 B |

| Body memory back to an array (`BodyBytes.Array`), 1 MB | 1,048,600 B | 0 B |

The changed-body cost that stays is the original and compressed text the content record keeps
(two UTF-16 strings) and the output array.
