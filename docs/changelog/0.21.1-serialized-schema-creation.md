# 0.21.1: first use of the content file no longer fails with "database is locked"

When several parts of the proxy used a new content file at the same moment, each one ran the
table creation on its own and they fought over the write lock. One of them could fail with
"database is locked", and a file could briefly show some tables without its version number.

Now the first user takes the write lock, creates the tables and sets the version in a single
transaction, and the others wait for it and find the work done. Nobody sees half a schema.

The request path keeps its one second limit. If it cannot get the lock in time it gives up, lets
the request go out without a record, and leaves no open transaction behind.

The worker that drains the queue had a related gap: when reading the queue failed, it marked that
change as seen and skipped the read on the next pass. It now marks the change only after the read
works, so a failed read is tried again.
