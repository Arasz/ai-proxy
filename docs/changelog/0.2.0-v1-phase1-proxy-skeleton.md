# 0.2.0 — the proxy skeleton

**Released:** 2026-10-21
**PRs:** #PR

The proxy now does the thing it exists to do, and the pieces it is made of sit behind
interfaces that a later phase can replace one at a time.

## What a user gets

Point an agent at the local proxy and the proxy works out which provider the request
belongs to, forwards it there, and brings the answer back. A request that is not provider
traffic is carried to the upstream the operator named for its path prefix, unchanged.

- A request whose path names a provider, such as `/v1/messages` or `/v1/chat/completions`,
  is forwarded to that provider's upstream with the caller's own credential.
- A request on a generic path whose body or headers name a provider is forwarded to that
  provider's upstream with the proxy's own credential, or refused when the proxy holds
  none. The caller's credential never travels to a provider the caller did not address.
- A request whose path and body name different providers is refused rather than guessed
  at.
- A request that names no provider, and matches no pass-through rule, is refused with
  `routing_unknown` and a body that says what was not known.
- A streamed response is relayed chunk by chunk, so a caller sees the first token as soon
  as the provider sends it.

## Configuration

Everything is configured through the environment, and the credentials live there and nowhere
else: `PROXY_ANTHROPIC_UPSTREAM`, `PROXY_OPENAI_UPSTREAM`, `PROXY_GEMINI_UPSTREAM`, the
matching `PROXY_*_KEY` variables, and `PROXY_PASSTHROUGH` for the path prefixes that carry
other traffic. The
[environment variable reference](../reference/environment-variables.md) has the detail.

## What did not change

The credential rule is the one from the research record, unchanged. So is the refusal: a
404 is still better than a credential at the wrong host.

The compression pipeline exists and does nothing. It is the seam the open question about
this project needs, and the question itself is still open.
