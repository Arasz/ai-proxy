# 0.3.0 — the content compression pipeline

**Released:** 2026-10-22
**PRs:** #4

The proxy now shrinks the tool output in a request before the provider sees it, and keeps
what it dropped so the original can be served back.

## What a user gets

An agent that runs a command, greps a repository or tails a log sends the output back to
the provider as part of its next request. That output is the part of the context that grows
without bound, and it is the part the provider pays for. The proxy now reduces it.

- A log keeps the lines that carry a signal, the failure, the timeout, the refusal, plus
  two lines at each end as anchors. A line at INFO level that says the request failed with
  status 503 survives, because the level alone is not the rule.
- A JSON document is compacted, and every value in it survives, down to the scale of a
  number.
- A directory listing passes through untouched, because nothing compresses a listing
  without losing file names.
- A mixed payload, an `ls` result and a grep result and a JSON blob in one tool output, is
  split by structure and each part is reduced by the rule that fits it.
- The bytes outside the tool output are what the client sent, byte for byte. The proxy
  changes the tool output and nothing else.

Nothing is ever rewritten. Every reducer keeps a subset of the text it was given, so a fact
that survives is intact, and a fact that does not survive is in the store.

## The original is kept, and it can be fetched back

Every request the proxy changes is written to a SQLite database, with the original, the
compressed text, the ratio and the path of the reducer that ran. The record is committed
before the request is forwarded, so the promise that the original is kept survives the
proxy dying. A store that cannot be written to is logged as a warning, and the request
goes out anyway.

The response carries the id in the `x-ai-proxy-content-id` header, and the original is
served back from `/content/{id}`. An id nobody stored is answered with a problem details
response, not with an empty body.

## Configuration

The stage is off until the operator turns it on, because it changes what the provider sees:

- `PROXY_COMPRESSION=on` turns the stage on. It is off by default.
- `PROXY_COMPRESSION_DB` says where the database lives. The default is
  `~/.ai-proxy/content.db`.
- `PROXY_COMPRESSION_MINIMUM` sets the smallest part that is compressed, for every kind.
  Without it, each kind has its own: 200 characters for a log, 100 for JSON, 512 for prose.
- `PROXY_COMPRESSION_MODEL` points at the extractive model's artifact. The model is not in
  this release, and the rule-based path runs until it is.

The [environment variable reference](../reference/environment-variables.md) has the detail.

## What did not change

The credential rule, the detection precedence and the refusal are the ones from the
research record, unchanged. So is the pass-through, which carries everything that is not
provider traffic without the proxy ever looking at the bytes.

The model-based path is not here. The measurements are clear that the rule-based reducers
are the ones that keep the answers, and that a summariser inverts the signal. The prose
path in this release is the rule-based one, and the model arrives behind the same seam.

The storage and the queue are described in
[ADR 0002](../adr/0002-the-store-is-an-adapter-and-sqlite-is-the-queue.md).
